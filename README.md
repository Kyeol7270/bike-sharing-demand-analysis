# 데이터 분석 포트폴리오 (with Claude Code)

자전거 대여 수요를 두 도시(워싱턴 D.C., 런던)에서 각각 회귀분석으로 예측한 프로젝트 모음입니다.
데이터 정제·EDA·모델링·검증·문서화까지 분석의 전 과정을 Claude Code(CLI)와 함께 진행했고, 두
프로젝트 모두 **판단과 방향은 제가 정하고, 실행·검증·기록을 Claude Code에 맡기는 방식**으로
작업했습니다. 이 저장소는 그 결과물이자 작업 과정의 기록입니다.

## 프로젝트

| | [01-washington](01-washington/) | [02-london](02-london/) |
|---|---|---|
| 데이터 | UCI Bike Sharing, 731일 (2011~2012) | Kaggle London bike sharing, 시간별→일별 변환 |
| train/test | 무작위 80/20 분할 | **2015년으로 학습 → 2016년 예측** (진짜 시간 분할) |
| 최종 모델 | XGBoost(튜닝) | LinearRegression(원-핫) |
| 홀드아웃 성능 | R²=0.897, MAE=435 | R²=0.769, MAE=3,120 |
| 가장 중요한 변수 | `yr`(연도) — 날씨보다 서비스 성장 추세가 더 크게 작용 | `t1`(기온) — 연도 정보를 뺀 상태라 날씨가 압도적 |
| 특이점 | Isolation Forest로 이상치 탐지 → 허리케인 샌디 등 실제 기상 이벤트와 대조 | CV 1위(XGBoost)와 홀드아웃 1위(선형회귀)가 갈림 — 작은 데이터에서 복잡한 모델의 함정 |

두 프로젝트는 독립적으로 시작했지만, 런던 프로젝트는 워싱턴에서 확립한 워크플로우와 규칙(시간별→
일별 집계 규칙, 회귀분석 파이프라인 구조)을 **그대로 복붙하지 않고 재검증하며** 재사용했습니다 —
예를 들어 워싱턴에서 가장 중요했던 `yr`(연도) 변수가 런던에서는 연도별 train/test 분할 때문에
오히려 써서는 안 되는 변수라는 걸 먼저 확인하고 계획에 반영하는 식입니다. 각 프로젝트 폴더의
`docs/WORKLOG.md`에 그 판단 과정이 그대로 남아 있습니다.

## Claude Code와 함께 작업한 방식

한 번에 "분석해줘"라고 맡긴 결과물이 아니라, 데이터 확인 → 정제 방침 결정 → EDA → 모델 설계 →
검증 → 결과 해석까지 각 단계마다 제가 방향을 정하고 결과를 확인하며 진행했습니다. 이 과정에서
Claude Code가 특히 도움이 됐던 지점:

- **결정 전에 항상 근거 있는 제안** — 인코딩 방식, 다중공선성 처리, 컬럼 포함 여부처럼 정답이
  하나가 아닌 선택지마다 "이렇게 하면 이런 이유로 이게 낫다"는 제안을 먼저 받고 검토·승인하는
  방식으로 진행했습니다.
- **결과물 자체를 의심하고 재검증** — CV 점수만 보고 최종 모델을 정하지 않고 진짜 홀드아웃으로
  다시 검증하게 했더니, 실제로 CV 1위와 홀드아웃 1위가 다른 모델로 나온 사례(런던 프로젝트)를
  놓치지 않고 잡아냈습니다. feature importance 차트에서 정렬된 값과 안 정렬된 배열이 섞여 라벨이
  밀리는 버그(워싱턴), 회귀 결론을 하드코딩해뒀다가 원본 재계산으로 수치가 다르게 나온 사례도
  그 자리에서 잡아 정정했습니다.
- **통계적 판정을 실제 사건과 대조** — 이상치·예측오차 상위 날짜를 그냥 "이상치"라고 끝내지 않고
  웹 검색으로 실제 기상 기록과 대조했습니다(허리케인 샌디, 2015년 UK 7월 최고기온 신기록, 2016년
  관측 사상 가장 따뜻한 크리스마스 등). 통계 모델의 판단이 현실과 맞는지 확인하는 습관입니다.
- **환경 이슈를 재발하지 않게 기록** — Windows 사용자 경로에 한글이 포함돼 `n_jobs=-1`이
  `UnicodeEncodeError`로 실패하는 문제를 발견해 `n_jobs=1`로 우회하고, 두 프로젝트 문서 모두에
  남겨 재발을 막았습니다.

각 프로젝트의 `docs/WORKLOG.md`에는 이런 시행착오와 중간 결정을 가공 없이 그대로 남겼습니다 —
최종 결과만이 아니라 **어떻게 그 결과에 도달했는지**가 이 포트폴리오에서 보여주고 싶은 부분입니다.

## 둘러보는 순서

1. 결과가 궁금하면 → 각 프로젝트의 `README.md` (한눈에 보는 결과, 결론, 한계)
2. 판단 근거가 궁금하면 → 각 프로젝트의 `docs/REPORT.md` (상세 분석 리포트)
3. 과정이 궁금하면 → 각 프로젝트의 `docs/WORKLOG.md` (세션별 작업 기록, 시행착오 포함)
4. 코드가 궁금하면 → 각 프로젝트의 `src/` (숫자 순서대로 실행되는 파이프라인)

## 저장소 구조

```
20th/
├── 01-washington/   # 워싱턴 D.C. — EDA·회귀분석·이상치탐지·오차분석 완료
└── 02-london/       # 런던 — 시간별→일별 변환, 2015→2016 예측 회귀분석 완료
```

각 폴더는 `data/`(입력) · `src/`(분석 코드, 번호 순서대로 실행) · `figures/`(시각화) ·
`tables/`(결과표) · `models/`(학습된 모델) · `docs/`(리포트·작업로그) · `README.md`(요약) ·
`requirements.txt`로 동일한 구조를 따릅니다.
